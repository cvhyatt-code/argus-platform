## What the sources change in D21 (for the build session)

This section is Chris's Cowork session's reading of the passages. The build session checks it against the quotes
above; the quotes are the evidence, not this summary.

**Confirmed as D21 states:**

- ID-token sign-in with no secret: `response_type` must include `id_token` (P4); the sign-in request needs the
  `openid` scope, `id_token` and a nonce (P3, P5); `form_post` is recommended for web apps (P6).
- The certificate fallback: confidential clients can use secrets or certificates, and Microsoft recommends
  certificates (P10, P12). A secret is "required for web apps" only in the sense that a web app must present some
  credential when it redeems a code (P11); a certificate replaces it (P12).
- Direct send stays out: Microsoft is working on disabling it by default (P18), and it reaches internal recipients
  only (P19).

**Changes and additions D21 needs:**

1. **The sign-in app registration must turn on ID tokens.** ID tokens aren't issued by default. The setup step must
   tick "ID tokens (used for implicit and hybrid flows)" under Authentication, or set `enableIdTokenIssuance` (P1).
   Without it, sign-in fails with `unsupported_response` (P2). The access tokens box stays off: the app never asks for
   an access token. Add this to D21 section 6 and to the setup steps given to the customer's admin.
2. **Validate the ID token with a library, not by hand** (P8). Web apps must validate (P7): signature, then claims
   (P9). Server mode names the library it uses (for example Microsoft's .NET token validation library, loaded from
   PowerShell 7) and tests it with fixtures, including an expired token, a wrong audience, a wrong issuer, a replayed
   nonce and a bad signature.
3. **The relay can't be used from any third-party hosted service, Azure included** (P15). D21 section 8 says
   "hosted in the cloud? check first". Change it to: SMTP relay isn't supported from a cloud-hosted server, Azure
   included. A cloud-hosted customer needs another route, which is the later `Mail.Send` decision.
4. **Microsoft recommends a certificate for the connector, and the IP address is the fallback** (P14, P16). D21 made
   the IP address the default because a certificate is a stored credential. That choice stands, but D21 should say
   it differs from Microsoft's recommendation, and why. The IP address must be static and not shared with another
   organization, and dynamic addresses aren't allowed (P16, P17).
5. **The default host name.** D21 says `<domain>.mail.protection.outlook.com`. The page gives the MX record's value,
   in the form `<YourCustomDomain>-com.mail.protection.outlook.com` (P20). Change the default to "the MX record's
   value for the sender's accepted domain", and have the setup step read it rather than build it.
6. **High Volume Email.** The page now says HVE can use OAuth as well as Basic authentication (P21). HVE stays
   excluded, because both methods need a stored credential, but D21's reason should say that, not "a password".
7. **PKCE with the fallback.** If the certificate code flow is ever used, it also sends PKCE, which Microsoft now
   recommends for confidential clients too (P13).
